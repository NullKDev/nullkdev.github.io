# Security

## Reporting a vulnerability

Please **do not open a public issue** for a security problem.

Use [GitHub's private vulnerability reporting](https://github.com/NullKDev/nullkdev.github.io/security/advisories/new),
or email <carlos.alarcon.dev@gmail.com>.

Expect an acknowledgement within a few days. This is a personal archive
maintained by one person, not a product with an on-call rotation — please treat
the timeline accordingly.

## What this site is

A statically generated site on GitHub Pages. There is no server, no database,
no user accounts, and no form that submits anywhere. Everything a visitor
interacts with — the Lab tools, the protected-content unlock — runs entirely in
their own browser.

That shape rules out whole categories of vulnerability, and it also rules out
some defences. Both halves are stated below, because a security policy that
only lists the wins is not a security policy.

## Content protection is a deterrent, not authorization

Some entries are encrypted with a passphrase (`protection: { mode: 'encrypted' }`).
The key is derived with PBKDF2 at 600,000 iterations, salted, and the payload is
decrypted client-side.

**The encrypted payload is publicly downloadable.** A static host cannot check a
password, because there is nothing running to check it against. Anyone
determined enough can attack the payload offline, at their own pace, with no
rate limit. It raises the cost of casual access; it is not access control, and
nothing genuinely sensitive belongs behind it.

The build fails if plaintext for a protected entry reaches `dist/`
(`bun run private:scan`).

## Headers we cannot set

GitHub Pages serves static files and exposes no header configuration. There is
no `.htaccess`, and a `_headers` file — the Netlify and Cloudflare Pages
convention — is silently ignored. Anything that must arrive as an HTTP response
header therefore cannot be set here:

| Control | Status |
|---|---|
| `Content-Security-Policy` | **Set**, via `<meta http-equiv>` on every page |
| `frame-ancestors` | **Not possible.** Ignored in a meta-delivered CSP |
| `Strict-Transport-Security` | **Not set by us.** `github.io` is on the HSTS preload list |
| `X-Content-Type-Options` | **Not possible** |
| `Permissions-Policy` | **Not possible** |

Clickjacking cannot be refused from a static host. Moving to a host that allows
response headers is the only real fix; until then this is a known, accepted
limitation rather than an oversight.

## The CSP is generated, not hand-written

`script-src` is `'self'` plus a SHA-256 hash for every inline script that
actually shipped. The hashes are computed from the built bytes after each build
(`bun run csp:apply`) rather than maintained by hand, because several inline
scripts carry content-derived data — a checked-in list would rot silently and
break production while local checks stayed green.

`'unsafe-inline'` is not used for scripts. It is used for styles, because a
static build has no per-request nonce.

**Google Analytics is the only third-party origin the site contacts**, and only
on builds where `PUBLIC_GOOGLE_ANALYTICS_ID` is set — a fork, a local build or a
preview reaches nothing. Consent Mode denies `ad_storage`, `ad_user_data` and
`ad_personalization`; the tag measures which entries are read, it does not
build an advertising profile of who read them.

Any other third-party request is blocked, and the demo or feature will visibly
fail. That is the intended behaviour — treat it as the policy working, not as a
bug in the policy, and prefer bundling the dependency over widening the
allowlist. That is how the `esm.sh` runtime import in the pretext demos was
found and removed.

## Supply chain

- Actions are pinned to commit SHAs, not tags. A tag can be moved; a SHA cannot.
- `GITHUB_TOKEN` is read-only by default; only the deploy job is granted more.
- `persist-credentials: false` on every checkout.
- Dependabot runs weekly with a cooldown, so a malicious release has usually
  been yanked before a PR proposes it.
- `bun run audit` gates every run at `high` severity and above.
- CodeQL and `zizmor` run against the source and the workflows.

## Scope

In scope: anything that lets an attacker execute code in a reader's browser,
alter what the site publishes, or reach the deployment pipeline.

Out of scope: the offline-attackable protected content described above, missing
headers that GitHub Pages cannot serve, and reports generated by a scanner
without a demonstrated impact on this site.
